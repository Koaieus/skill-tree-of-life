**Headline verdict.** The single-player game is playable, teachable in person,
and people got real runs out of it. Two things it is not yet: **playable over
the network** (one versus attempt, blocked at load) and **legible without a
human sitting next to you**. The most-cited difficulties were not bugs — they
were *understanding*, *early-run balance*, and one attack type being
structurally outclassed.

### 2.1 LAN-01 — versus did not load *(Blocker)*

> **Owner report 2026-09-07:** *"versus over LAN → peer hung at 0% loading
> screen after host hits 'start'; recent commits tried to address that, didn't
> verify it now works"*

One attempt, one failure, no second attempt. Two netcode fixes landed **during
the LAN window** and plausibly cover it — `af50255` *"a joiner waiting for its
world can no longer be left on a black screen"* and `424a51a` *"GameRoot's
refusal handler must not share a name with the dev sandboxes' own"* — but
**neither has been verified against two physical machines.** `mise run mp:e2e`
runs two processes on one host, which is a weaker claim than the failure mode.

This is the whole reason #665 exists ("OWNER-RUN, not drone work — versus smoke
test: one real run across two physical machines and two operating systems"), so
the finding is recorded there rather than as a duplicate.

**Filed:** comment on #665. That issue stays open.

### 2.2 LAN-02 — the AI's +30 WIS head start makes the early game a coin flip *(Major)*

> **Owner report 2026-09-07:** *"enemies 'cheat' with +30 WIS head start, so it's
> like a coin flip 'will i get shrekt by an OP enemy at turn 2, or do i see no
> enemies yet'. many runs end after 1~3 turns where an overly strong enemy pops
> up and just oneshots you with a too powerful spell"*

The failure is bimodal, and both halves are bad: either an overpowered enemy
finds you immediately and the run is over before it is understood, or nothing
finds you and the early game is empty. For a room of first-time players being
taught the game, a turn-2 one-shot is the worst possible first impression —
it teaches nothing and reads as arbitrary.

Note the coupling to LAN-03: the head start is a *lobby default* as much as a
balance number, so the two are likely fixed together.

**Filed:** #758

### 2.3 LAN-03 — the single-player lobby cannot give an AI a plain core, and cannot template rows *(Major)*

> **Owner report 2026-09-07:** *"single player lobby: entities should be able to
> be picked as 'basic core'. so they no longer 'cheat'. ideally, we could also
> set a 'preset row' for AI entities, e.g. set its core class or camp (with the
> option to split camps) and then the AI rows as they are appended (by player
> using the UI to select more AI opponents) get templated from the one preset
> row, and also update if the preset row changes UNLESS the individual row has
> been altered"*

The worked example the owner gave, which is the acceptance criterion in
miniature:

1. Set preset to *basic enemy core* → all AI slots take it.
2. Raise the AI count → the new rows appear already holding *basic enemy core*.
3. Set **one** AI to *Serpent core* → only that row changes.
4. Change the preset to *balanced core* → every row follows **except** the
   Serpent one, which was explicitly overridden.

> *"1 click could change N AI slots, better than clicking all of them
> individually (UX)"*

The override-sticks rule is the hard part and the part that makes it worth
building; a preset that stomps bespoke rows is worse than no preset.

**Filed:** #759

### 2.4 LAN-04 — magic damage does not scale legibly across three orders of magnitude of INT *(Major)*

> **Owner report 2026-09-07:** *"INT modifiers were way off. or actually on
> point, just the scaling into magic damage was off. someone hit ~20k INT levels
> in their first playthrough (also their most successful one, they were more
> lucky than they realized). 20k INT is intentional, it's fun to have a runaway
> stat like that. but we should adjust our damage scaling so that .5k INT and 1k
> INT 5k, 10k, 20k int are in some way different yet comparable."*

**The runaway stat is not the bug and must not be "fixed".** A player reaching
20k INT on their first run is a feature and was that player's best run. What is
wrong is the *transfer function*: the span from 0.5k to 20k INT must produce
outcomes that are distinguishable from each other and still commensurable — a
20k mage should be frightening, not a different genre of object.

This is an owner-tuning problem with an agent-testable shape; see
`feedback_owner_tunes_agents_test` — the curve is the owner's call, the
property test that 0.5k/1k/5k/10k/20k stay ordered and bounded is not.

**Filed:** #760

### 2.5 LAN-05 / LAN-06 — the game is not teachable without a human *(Major)*

> **Owner report 2026-09-07:** *"spells were hardest to understand (many gates,
> and 'degree' is a math concept they'll have to learn, which they picked up
> quickly but this game lacks any form of a tutorial (wasn't in the priority for
> LAN given i was there to guide). melee might've been even harder to teach.
> some pointers in the command tray or next to icon like 'select pivot' would go
> a long way. […] ranged attacks: most intuitive as soon as they'd understand
> 'leaf node' c.q. 'degree 1'"*

The difficulty ranking observed in the room, easiest to hardest:

1. **Ranged** — intuitive *immediately* once "leaf node = degree 1" lands.
2. **Spells** — many gates to hold in your head at once.
3. **Melee** — "forging a blade requires some skill already".

The encouraging half: **`degree` itself was picked up quickly.** The graph
vocabulary is not the barrier — the barrier is that nothing in the UI tells you
what the game is currently waiting for you to do.

Three remedies, in ascending cost, all owner-proposed:

- **Inline pointers in the command tray / beside the icon** — literally the words
  *"select pivot"* at the moment a pivot is what's wanted. Cheapest, and the
  owner's judgement is that it *"would go a long way"*.
- **The armed spell's icon on the cursor** (LAN-06) — *"we got plumbing set up
  perfectly for that already with the `Armed` stuff"*. Small, and it answers
  "what am I even holding right now".
- **Interactive tutorial, or a floating few-second pre-recorded clip** —
  *"would help magic most of all"*. Real scope; the milestone
  `Onboarding & accessibility` is where it belongs.

**Filed:** #761 (hub) + #762

### 2.6 LAN-07 — a low-end machine could not hold framerate while nothing was happening *(Major)*

> **Owner report 2026-09-07:** *"on a 'used to be gaming laptop' which i call The
> Craptop i tried playing it and i doubt we got 30 fps out of that, let alone
> 144Hz. and that is while just stationary during a turn, nothing happening in
> the game. i wonder what the cause was, CPU or GPU and i'm 80% sure the
> **fake-3D core halo gimbals** is the prime suspect. but we should run a
> performance test for this. like my PC is a beast and can do 144Hz but even
> that one has struggles with some of what we do, and we need it scalable and
> generally (esp if turn is stationary) be comfortably in the range of 144Hz,
> not 'just in time'."*

Three separable claims, worth keeping separate:

1. **A stationary turn is not free.** Idle cost is the floor of everything; if
   the floor is expensive, no amount of headroom during action survives.
2. **The cause is unattributed.** The suspect is the fake-3D core halo gimbals,
   at 80% confidence — but *this repo has been wrong about that twice*, and both
   times the answer was a quadratic CPU walk rather than the shader
   (`feedback_measure_cpu_before_gpu`). Measure before fixing.
3. **The dev machine is not evidence.** The owner's GPU is an RX 7900 XTX
   (`user_gpu_is_high_end`); local timings are best-case. The Craptop is the
   first real data point from the other end of the range, and it says the North
   Star ("2000 nodes, 144Hz, 1440p" — FOCUS.md) is not currently met with margin
   anywhere but on the beast.

**Filed:** #763

### 2.7 LAN-08 — the spell tooltip is one block where it should be three, and too long *(Major)*

> **Owner report 2026-09-07:** *"spell tooltip: we really need to separate this
> into i think at most 3 (or 4) sections, each clearly marked and derived from /
> provided by resources composed in the SpellDef:*
> 1. *initial target gating / targeting → from where can I cast this, and what
>    can i hit from there (euclid? hops?) — targeting filters (what nodes can it
>    hit initially, like friendly or hostile or unallocated or anything in
>    between)*
> 2. *what does it do when it arrives — apply damage / how much (initially)*
> 3. *where does it go next — propagation filters + effects + 'step' (the Step
>    classes i'm not sure if/how we want to keep this as it feels like it's to
>    some extent stealing the role of another resource like propagation*
>
> *the spell descriptions should be.. snappy. nobody is gonna read a wall of
> text. the spell tooltip should provide brief characteristics and some
> bigger/more detailed explanation is neat but maybe not for in a spell tooltip
> (could save it for somewhere else)"*

Two things in one finding, and they reinforce each other: **the sections must be
derived from the composed resources on the `SpellDef`, not hand-written per
spell** — that is what stops the tooltip drifting from the spell — and **the
prose must be short**, because at the table nobody read the long version.

It also surfaces an unresolved design question that is *not* a tooltip problem:
whether `Step` is stealing propagation's role. That fork should be settled
before the tooltip's third section is designed around it.

**Filed:** #764

Separately and much smaller: **spell tooltips rendered behind modals and other
UI** — a z-order/layer bug, not a content problem.

**Filed:** #765

### 2.8 LAN-09 — mana is a stat that does nothing *(Major)*

> **Owner report 2026-09-07:** *"mana, mana regen: useless stats. either we
> remove them, or rework their scaling, as of now they just sit in the way. mana
> is often a delimiter for spellcasters, but entities are more constrained by
> Action Points than anything else — you can have ∞ mana and still just cast 2
> spells (because of having just 2 action points)"*

The genre expectation (mana gates casting) is not what this game does; AP gates
casting, and mana is a second gate that never binds. A resource that never binds
is worse than absent — it occupies UI, occupies stat-board space, and teaches
new players to watch a number that cannot hurt them. The fork is remove vs.
rework, and it is a design call.

**Filed:** #766

### 2.9 LAN-10 — there is no tempo *(Major)*

> **Owner report 2026-09-07:** *"action points: no way to gain tempo? regain them
> during a turn? possibly: get 1 AP on landing an entity-killing blow, max 1 of
> those per turn (killing a Blocker would also count, making killing them more
> fun instead of tedious and a drag). but we should keep a broad perspective for
> other opportunities of increasing or replenishing AP. a Keystone granting +1
> max AP could be sick, a rare loot. but we should consider: what player action
> would thematically best fit a skilltree-occupying entity such that they should
> be rewarded more temporary or max action points?"*

If AP is the true constraint (LAN-09), then AP is where the interesting
decisions live, and right now it is a flat allowance with no way to play around
it. Two concrete proposals plus one open design question:

- **+1 AP on a killing blow, max one per turn**, Blockers included — which also
  converts Blockers from *"tedious and a drag"* into a tempo opportunity.
- **A Keystone granting +1 max AP** as rare loot.
- **The open question, which is the real one:** *what player action thematically
  deserves an AP reward from an entity that lives on a skill tree?* That wants
  a design pass, not an implementation.

**Filed:** #767

### 2.10 LAN-11 — the turn-order bar hides the queue it exists to show *(Minor)*

> **Owner report 2026-09-07:** *"turn order bar represents your initiative
> (0..100+) but at a tie (currently: always) of entities having 100+ initiative
> (meaning they can take a turn) it just shows full. […] say there are 5 entities
> and they all got 10 initiative, then turnmanager ticks +10 on each until one
> has reached 100 or more, and these will ALL reach it in the same tick so each
> gets served a turn before the next turnmanager tick. going from 0..100
> initiative is helpful but 99% of the wait is in the 0..4 other entities that
> take a turn before you and the bar should ideally reflect that. which is tricky
> given the bar would need some combination of actual initiative and queue
> (including tie-breaking)"*

The bar answers "how close am I to being allowed to act" and the player is
asking "how many people go before me". With uniform initiative — *currently
always* — those diverge completely: five entities all read 100% full and the
bar conveys nothing at the exact moment it matters most.

Flagged by the owner as tricky, because the honest display is a *composite* of
the initiative fill and the tie-break ordering.

**Filed:** #768

### 2.11 LAN-13 — procgen rolls too many addons, and they sit where melee needs to go *(Major)*

> **Owner report 2026-09-07:** *"the procgen NodeAddons rolling need to be
> controllable from lobby. or disabled. currently there's a LOT of addons which
> adds to the visual clutter. without them the game should be playable too. also
> they get in the way of melee attacks by occupying an addon slot (which made it
> harder for me to explain like 'pick the pivot here, then apply clamp to the
> next 1~2 nodes... oh no wait these are occupied uhhh let's find a different
> pivot..'"*

Three costs from one setting. **Clutter** — addons draw geometry outboard of the
emblem, so a densely-addon'd graph is a busy one, on a board new players already
struggled to read. **Blocked melee** — an occupied slot cannot take a
`ClampAddon`, and the owner's teaching moment says the rest: a player learning
melee should be choosing a pivot on *topology*, not on which nodes happen to have
a free slot. **Untestable baseline** — the owner's bar is that the game is
playable without addons at all, and there is currently no way to check.

The knob exists already: `AddonPolicy.slot_count_weights` defaults to
`{0: 60, 1: 25, 2: 12, 3: 3}`, about 0.55 addons per node, authored per content
module. What is missing is the lobby row that exposes it — and, being run shape
rather than seat policy, it belongs to the roster every peer reproduces.

**Filed:** #770

### 2.12 LAN-14 — the AI never builds its weapon *(Major)*

> **Owner report 2026-09-07:** *"AI should really consider building up their
> weapon by placing a clamp node on the first 1~2 nodes in blade UNLESS they had
> achieved triangle-based full rigidity near the pivot (like a ~truss bridge)"*

The AI swings whatever blade its territory happens to hand it. Clamping the
joints nearest the pivot is the cheapest durable investment a melee entity can
make — a floppy root bleeds the swing into its own hinges instead of into the tip
— and it is the sort of preparatory play that makes an opponent read as having a
plan.

The exemption the owner names is not a nicety, it falls out of the
implementation: `clamp_addon.gd` notes that *"already-triangulated joints get
redundant constraints; redundant ≈ no-op for PBD"*. A clamp on a triangulated
joint is a wasted slot. So the AI has to ask a **graph** question — is this joint
in a triangle — before spending an **addon** slot, and slots are contended
(LAN-13).

**Filed:** #771

### 2.13 LAN-15 — a spiked node is a full, unlimited counter to melee *(Major)*

> **Owner report 2026-09-07:** *"melee is severely outclassed by the others
> because spiked nodes provide *full* defense against it, potentially
> neutralizing most or the entire blade. this should be tweaked: either make a
> spiked node pop only 1 incoming blade until owner's turn starts, or instead of
> pop it 'reduces' damage, and need to review what happens to the blade iff
> something gets popped (does it cascade to other blade elements that would no
> longer be connected to the pivot?). needs a full desing sesh"*

**The cascade question has an answer already, and it is the bad one.**
`blade_pop_resolver.gd` (#170): killing a vertex disconnects everything
downstream of it from the pivot, and every vertex no longer reachable through
surviving edges is disintegrated. The popping contact itself deals no damage, and
nothing exhausts a spiked node — it pops every vertex that reaches it, without
limit.

So one spiked node contacted early in a sweep can delete most of an attack that
took several turns of territory to assemble, for free. Ranged and magic have no
equivalent: nothing voids a spell mid-propagation or an arrow's payload outright.
Melee alone faces a binary, unlimited, no-cost counter sitting on a common addon.

The owner names two directions — rate-limit the pop to one per node until its
owner's turn starts, or replace the pop with damage reduction — and flags that
**both require re-examining the cascade**, since the cascade is what turns a local
counter into a blade-wide one. Marked as needing a full design session, and it is
also where `skill_node_addons.md`'s standing **`FLAG` — Thorns vs Spikes, resolve
before either ships** finally has to be answered.

**Filed:** #772

### 2.14 LAN-12 — versus is the balance oracle *(Note, no issue)*

> **Owner report 2026-09-07:** *"balance being off is in versus less of a thing,
> like: if two 20k INT players meet face to face, they both use the same rules
> still which allows seeing what's REALLY imbalanced — a smart massive-STR player
> vs a smart massive-DEX player vs a smart massive-INT player? sounds like a real
> test of balance"*

Recorded as strategic context rather than a defect: **absolute** numbers being
wild (LAN-04) matters far less in a mirror than **relative** power between the
three build axes, and versus is the only format that measures the latter
honestly. It raises the value of LAN-01 beyond "a mode is broken" — versus is
also the balance instrument this project does not currently have.

No issue filed; this belongs to the versus lane (#665) and to whatever balance
pass follows it.

## About this format

**What a playtest report is here:** a dated, immutable record of one event —
who played, what they played, what happened, and what each observation became.
It is the *provenance* layer. It is not a task list, not a status page, and not
a design doc.

**Why immutable:** `docs/FOCUS.md` has been rewritten twice for the same failure
— per-issue prose in a mutable document is *"irresistible to append to and
invisible to prune"*. A report that is never edited cannot rot; it can only be
superseded by the next report.

**The three-way split:**

| | Answers | Mutability |
|---|---|---|
| **Playtest report** | *what happened, on this date, to these people* | immutable |
| **Issue** | *what we are going to do about it, and where that stands* | live |
| **ADR** (`docs/adr/`) | *why we chose this over that, and what we rejected* | immutable, superseded not edited |

**Every finding gets a disposition.** Filed with a number, or dropped with a
reason, once, at write time. Nothing is left implicit and nothing is updated
later — if a finding's issue gets closed, that fact lives on the issue.
